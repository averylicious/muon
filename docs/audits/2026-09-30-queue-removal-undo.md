# Queue removal Undo ownership — 2026-09-30

[#241](https://github.com/averylicious/muon/issues/241), main base `a58049bda54820a3f346478aa24c78099ec3bf69`. QueueScreen previously waited for the snackbar, then added the saved track at its old index regardless of a queue/controller replacement in between.

`TauonTrack.mediaItem` now assigns a fresh temporary occurrence UUID whenever Muon constructs/inserts each item. The song/cache/media IDs and stored song record stay unchanged; metadata extras preserve the occurrence through controller serialization. This identifier is not authentication or a persisted schema. Both playlist replacement paths map each track through this factory; song insertion does too. Removal records the old occurrence for ownership; successful Undo creates a fresh reinserted row identity, preserving the song metadata so old dismissed-state storage does not reattach.

`QueueRemovalUndo` captures the ordered, unique (media ID, occurrence key) list remaining after a validated Next up removal. It restores once only if that exact ordered occurrence list/controller/edit command survives. A freshly built identical-song queue, duplicate reorder or another insert/remove invalidates it. Position/shuffle/source-duration changes preserve the canonical list. Missing/cloned keys and empty queues cannot establish ownership and do not offer Undo. Reusing the exact same already-tagged item objects intentionally preserves those occurrences; the app's fresh playlist construction does not do that. QueueScreen checks its latest controller, explains refused Undo, and closes its temporary action on completion/cancellation (including an already-cancelled launch). No player listener remains.

This is separate from insertion Undo #224 and row-action/drag snapshot guards #219; preserve both when reconciling QueueScreen, metadata extras and PlaybackService changes (#221 also touches the service). No media/cache IDs, lyrics or stored song schema change. It cannot make a remote session's still-undelivered changes atomic with a UI action; a received/current controller snapshot is the verification boundary.

Eleven tests use the actual helper and production media-item factory with ExoPlayer; two connect a real MediaController/MediaSession using the production callback and command/result barrier. They cover exact duplicate/metadata restoration, new identical-song replacement, different replacement/clear, duplicate reorder, position/shuffle survival, stale/closed rows, normal asynchronous acknowledgement, received session replacement and missing/cloned keys. No prepare/audio/network. Initial run407 compiled but failed the normal-controller regression: the first listener/timeline-based design invalidated its own asynchronous acknowledgement. It was not a pass or acceptable behavior; the production correction keeps that regression. Latest-head CI/report evidence belongs on the PR; phone snackbar/reconnect behavior remains pending.

Real acknowledgement tests determine behavior rather than assuming a timeline object or callback generation remains identical. No legacy-controller/Binder cross-process guarantee is inferred.

## Stable duplicate rows (#243)

QueueScreen now uses valid unique occurrence keys for normal Muon queue rows. Removing an earlier identical song or changing playing order retains every survivor's own key; the old per-ID occurrence-numbering fallback cannot establish that. A collision-free fallback remains for legacy/missing/cloned metadata, with no claim of stable identity for those ambiguous items. No global library-list key change. Two additional actual ExoPlayer cases verify removal/reorder key survival, fresh Undo row identity, stored song metadata preservation and fallback uniqueness. Phone swipe/drag/Undo visual behavior remains pending; stable source keys alone do not prove Compose saved-state or animation behavior.
