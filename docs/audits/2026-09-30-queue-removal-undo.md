# Queue removal Undo ownership — 2026-09-30

[#241](https://github.com/averylicious/muon/issues/241), main base `a58049bda54820a3f346478aa24c78099ec3bf69`. QueueScreen previously waited for the snackbar, then added the saved track at its old index regardless of a queue/controller replacement in between.

`QueueRemovalUndo` attaches a temporary listener before removing a validated Next up entry, captures the playlist-change generation and remaining full item list afterward, then permits one restoration only while that ownership, editable command and list remain. Playlist replacement/reorder/add/remove invalidates even with identical IDs/items; position/shuffle changes alone do not. Empty results cannot claim surviving ownership. QueueScreen also checks its latest controller and explains a refused Undo. Listener cleanup runs after snackbar completion/cancellation and even if the coroutine scope was already cancelled when launched; it does not become a lifetime player listener.

This is separate from insertion occurrence Undo #224 and row-action/drag snapshot guards #219. Reconcile their QueueScreen change during integration; retained IDs, cached metadata, lyrics and storage schemas remain unchanged. The helper rejects a current-playing/out-of-range/mismatched removal before reading an invalid position, consistent with Next up's scope. It cannot make a remote controller's still-undelivered state atomic with the service; source/phone QA must distinguish that boundary.
