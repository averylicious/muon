# Bounded derived artwork-cache reads (#253)

The two-pipeline limit from #619 bounds concurrent loads, not each allocation. HTTP artwork responses are capped at4MiB and saved-copy covers already use bounded reads. Derived ArtworkDiskCache.read used File.readBytes with no entry cap, however; an older/corrupted enlarged private cache entry could allocate its full size before decoding. This is a source-confirmed missing bound, not evidence of an attacker, an observed phone OOM or a reproduced corrupt user cache.

Derived entries now have an8MiB cap. Raw covers retain the unchanged4MiB network cap; smaller decodes can be re-encoded as PNG and exceed their compressed input. The8MiB allowance accommodates the current at-most768px scaled short side/approximately2048px long-side decoder bound. Unsupported oversized cached entries become misses; normal fetch/decode may replace them. Existing URLs/identity filenames, expiry, total128MiB LRU, saved covers, network guards and signing/release behavior are unchanged. An oversized new write does not replace a good entry. No saved/original music is removed.

The opened Okio stream must also fail the cap+1 request before readByteArray, so a file growing after the length observation cannot cause an unbounded allocation. Streams close in use on success/refusal/error. The bound is per operation, not an exact whole-process heap guarantee; two operations and buffered/result copies may overlap. Future decoder bucket/dimension changes must re-evaluate the derived-entry allowance.

One focused actual-cache regression covers exact-boundary round trip, oversized sparse-file miss, unrelated-cover preservation, successful later replacement and refused oversized write preserving the existing entry without temporary files. Existing expiry, identity, replace/LRU/directory tests remain. CI is the first Android compile/test; source self-check is not independent review. This change does not require altering a phone cache to establish the bound.
