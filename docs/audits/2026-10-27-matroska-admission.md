## Initial production boundary

The actual factory MatroskaExtractor stays in place. Its public forwarded input observes DefaultEbmlReader’s real ID/size varint reads. Native VarintReader uses distinct allow-end first-byte reads for element IDs and sizes; sample/lacing varints use non-allow-end reads outside that header state. The observer admits a declaration after its last size byte arrives, before readString/binaryElement allocates. It retains unfinished varint state across I/O reopen; seek resets that state consistently with the native reader reset. No replacement processor/library fork or constructor-default reconstruction. Fixed short audio-format refusal messages match the separately verified WAV notice helper, preserving old tag/art notices for other formats and exposing no source path or server text.

Exact native string IDs and non-media binary IDs are admitted against4MiB per element,16MiB aggregate declared payload and4,096 position-keyed high-water entries. Known stream and signed/overflow bounds are checked; SeekID also fits its actual fixed4-byte target. The bounded ledger keeps costs on seek because native track/chapter objects can remain retained. Rereading a prior payload position charges only growth. Unknown-length truncated bodies remain bounded and keep native EOF behavior. Segment/Cluster and media Block/SimpleBlock lengths are not whole-file/audio caps.

Sniff forwarding checks peek/advance size before DefaultExtractorInput can grow its buffer, with a64KiB window from the input position. This covers the unknown-length EBML header route in the raw proof. Existing ID3 admission still runs first. An invalid over-width/zero ID fails closed rather than entering the native byte-resynchronization path. That is a deliberate damaged-input compatibility difference needing later acceptance.

These are proposed resource policies, not a universal heap bound. Retained strings can also need character/object overhead. Ledger size is bounded, but other private-codec nested counts, sample/lacing/subtitle/output buffers, decoder/GC overlap and external metadata copies are **not cleared by this first step**. The native-frame policy below has a separate legitimate live-WebM compatibility cost. Do not label source allocation evidence a device crash/exploit or #671 diagnosis.

## Nested Vorbis private headers

MatroskaExtractor.Track.parseVorbisCodecPrivate sums Xiph info/skip laces, checks the first packet marker, then allocates info before arraycopy verifies its backing. A bounded private payload can amplify those laces, so the first leaf cap alone is insufficient. The observer checks the real delivered codec-private array before native Track format initialization, with wide lengths/backing and all three packet markers. CodecID may precede or follow CodecPrivate; retain one reference to the existing native array until TrackEntry changes, without copying it. Trailing-zero CodecID padding retains native semantics. Seek keeps the current codec context like native currentTrack; header observation resets. Other private codecs are not certified by this Vorbis-specific correction.

## Track, chapter and cue retention

Native TrackEntry initialization stores tracks keyed by the int-cast TrackNumber, ChapterAtom stores nonzero long UIDs, and CueTrackPositions can append a per-track CuePointData before the seek map builds four additional arrays. The observer reads actual delivered fixed-buffer integer values before those callbacks. Proposed limits admit128 distinct observed track keys (including native default0) and4,096 nonzero chapter UIDs. These bounded sets survive seek, like native maps; overwritten/unsupported keys may conservatively over-count. Metadata payload admission remains separate.

At most65,536 CueTrackPositions headers are admitted before a final seek-map callback. That bounds candidate cue objects, per-track lists/keys and the primary track’s four ChunkIndex arrays; invalid/empty positions may over-count. A forwarded output preserves the actual map and records successful delivery, after which native ignores later cues and the observer stops charging them. Native seek clears unfinished cue lists only before a map is sent, so the unfinished counter resets only then. This is source/retention admission, not a global byte-accurate heap/GC estimate.

## Retained master frames and unknown-sized Clusters

[EBML RFC8794 section6.2](https://www.rfc-editor.org/rfc/rfc8794.html#section-6.2) permits unknown-sized masters with schema-defined termination; [Matroska RFC9559 section5.1.3](https://www.rfc-editor.org/rfc/rfc9559.html#section-5.1.3) allows unknown-sized Clusters. These are not inherently malformed or nested sibling data. Pinned DefaultEbmlReader nevertheless tracks each recognized master as content-position plus the literal size-varint value, popping only when the current position reaches the top frame’s end. Eight-byte unknown-sized sibling Clusters can therefore retain additional native frames even at EOF.

The candidate mirrors the exact30 native master IDs/end positions and refuses before a4,097th retained frame; this is a resource limit on native storage, not a Matroska schema-depth rule. Mirror frames pop before new IDs and at successful read returns, before any internal backward source reopen following an end-master callback. Explicit seek clears this mirror like native reader.reset. No synthetic ends, byte rewriting, constructor/flag changes, reflection or library fork in production. Test-only reflection observes modest actual native frame counts.

**Compatibility policy still needs acceptance:** a legitimate long/live WebM using many eight-byte unknown-sized Clusters can hit this limit. Known-size sibling Clusters normally pop and do not accumulate toward it. No duration estimate is universal; it depends on Cluster cadence. This safeguard does not repair upstream EBML schema handling and is not silently called free compatibility. No frozen RC is changed.

## Proposed unfinished Xiph header bound — 2026-10-28

Separate from the approved4MiB text-packet policy: pinned binaryElement's Xiph-lacing loop repeatedly grows readScratch before audio/sampleData. It can continue on actual delivered255 bytes without returning to the progressive loading interval; native scratch is outside the SampleQueue allocator. This is not tiny-declaration amplification or proof of a phone OOM, an indefinite hang or#671's cause. Root source assessment and a fresh allocated Opus5.5 High-requested read-only assessment agreed on this selected path; the raw native-only witness is #727/e9f17bfd and still needs its own CI. No new frozen gate.

The draft proposes64KiB of requested Xiph scratch prefix per Block/SimpleBlock. One scalar marks the native Block body until the next element or seek; it checks only pinned scratch-extension calls (3-argument readFully, one byte at offsets4+), not an entire audio packet or a retained array's spare capacity. Native backing may already have doubled before interception; old/new arrays and whole heap are not byte-exact bounded. Audio payload uses DataReader.read; video NAL/encryption reads are small/fixed or start at offset0, while subtitle-body reads retain their independent4MiB policy. No new output wrapper, track map, payload copy or codec/lacing parser. Recheck these call shapes on a dependency upgrade.

A new actual-native control refuses unfinished audio/text headers at an injected64-byte threshold for both Block variants and after seek; a completed two-sample Xiph control still delivers both samples. Existing large unlaced AAC and small/longer native subtitle controls use that tiny header limit to distinguish payload from header. These are extraction/source controls, not decoded sound or device compatibility. Current proposal awaits its own CI and user decision; do not integrate the new64KiB policy solely because earlier .1604/.1624 passed. Rare legitimate packets with unusually large encoded lacing headers could be refused.
