# Bound playlist-label and lyrics display input (#253)

Track tags already have a16KiB record budget. A single playlist label could nevertheless consume almost the full16MiB metadata-response allowance, then reach Compose; lyrics had the same response-sized string path into one selectable Text. Structural value/array limits do not bound a single large string's text-layout work. These are source-supported missing per-display bounds, not an observed user OOM/ANR or evidence of a hostile server.

Playlist ID+name now allow at most16KiB UTF-8, checked first by character count before allocating encodings, both at the API projection and aggregate/retained-load admission boundary. Numeric-ID and duplicate/count/order rules remain. The same generous scale already used for a track record applies per label; total accepted library budgets stay. Oversized labels reject the response with a fixed short resource error and do not truncate/publish a prefix.

Lyrics get a512KiB wire-body limit before bytes/string/DOM projection, plus at most64Ki UTF-16 code units and2,048 lines before selectable text. CRLF counts once; CR/LF/NEL/Unicode line/paragraph separators count.512KiB also accommodates a64Ki-unit lyric encoded with six-byte JSON escapes. Empty/missing/null and literal string null behavior stay. Accepted text is unchanged; oversized responses give a fixed error without reflecting lyrics. Other endpoint wire limits remain16MiB. Individual caps are not a whole-process/native-layout guarantee.

Three focused existing-fixture tests cover actual public playlist projection and aggregate admission at encoded/Unicode/large-ID bounds, accepted/refused lyric text/line boundaries, and exact512KiB versus cap+1 response bytes through real OkHttp/platform JSON. No new test class/dependency or Compose test; CI is first compile/run. Normal lyrics/playlist display and subjective user acceptance remain pending; do not intentionally render response-sized strings on a phone to obtain a crash.
