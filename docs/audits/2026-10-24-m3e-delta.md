## Finite next-release gates

1. **Candidate integration:** pass required checks on #674/#675 final heads, review the combined changes, and pin one combined M3E candidate. Moving the experimental branch changes the candidate; changed paths need proportional re-review.
2. **Targeted acceptance:** predictive Back/rapid swipe ownership, menu routing, queue Undo/duplicates, Saved actions, recent Search/Clear, seek/volume TalkBack, portrait/landscape and playback. Use Diagnostic for automated investigation so the user's everyday Canary is preserved; validate the actual release configuration before RC approval.
3. **#671 disposition:** collect useful evidence if it recurs. A serious reproducible streaming failure needs a fix or explicit informed release disposition; do not call absence of a late log a pass or require speculative router/ROM changes.
4. **Promotion engineering:** current branch-direction/alpha-ancestry guard deliberately rejects M3E on main. Prepare a reviewed, bounded promotion-policy/integration change after candidate acceptance, preserving package/signing/feed behavior. Do not disable the guard or squash history merely to get a green check.
5. **Release decision:** explicit user RC/Stable approval and version/tag/publication request. v0.2.0's release delegation is not reusable permission.
