## Confirmed route

`OfflineStore.removeSaved` and `removeAll` enqueue on the single saver without reserving a preparation slot. The existing removal-delivery/ownership checks run later, after closures/context/references can accumulate while the worker is busy. New saves already reserve `savePreparation`; this gap is before the removal checks, not a failure of their byte/identity protection. No OOM, lost bytes or reproduction of #646's historical refusal is claimed.

## Candidate and boundaries

One shared per-Store atomic `removalPreparation` covers pending and running single/Delete-all checks. Admission happens before enqueue; a pending preparation gives immediate busy feedback and retains no additional storage job. Release occurs in the worker's finally, or after the known saver rejects before acceptance. Queued work captures application context. The first operation keeps all existing census, move exclusion/revocation, confirmed-byte/native-closure and route-specific service-delivery checks. Played/partition routes are not newly refused merely because a legacy delivery is pending. Delete-all still revokes moves immediately as before, even when it cannot proceed.

This bounds user removal preparation only, not every saver job or the complete heap. It does not change storage formats, ownership authority, restart recovery, package/signers, receipt timeout or the separate #646 error-classification candidate. A busy response is an actual pending operation, not an ownership refusal. Unexpected operation exceptions still unwind through the existing paths; the preparation slot is released only on actual worker exit.
