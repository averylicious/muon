## Confirmed source gap

`ReplayGain.trackLoudness(Metadata)` accepted only `VorbisComment`. Pinned Media3 exposes MP3 ID3v2 user text as `TextInformationFrame`. rsgain writes ReplayGain gain/peak in ID3 TXXX frames and supports lowercase descriptions. A tagged MP3 therefore looks untagged to Muon and receives the existing library estimate/no-tag notice. An initial lowercase-Xiph hypothesis was withdrawn after checking the constructor: Media3 already uppercases those keys, and Muon already handles them. This is a format-coverage gap, not a reproduced device regression or proof that the user's particular library contains affected files.

Source evidence: published Google Maven `media3-extractor:1.11.0` sources SHA256 `76404d34549e50b93f16c94119aace19dee06be9068c45a3d4f8ed5289e4eb3e`, `Id3Decoder.decodeTxxxFrame`, `TextInformationFrame`, `Mp3Extractor` track-format metadata and `VorbisComment` constructor. rsgain [pinned ID3 writer](https://github.com/complexlogic/rsgain/blob/aae8cc74190de9dafce41576f3e407e62420a51d/src/tag.cpp#L691). No library/API upgrade.

## Additional M4A finding

The same adapter also ignored `InternalFrame`, which pinned `MetadataUtil.parseInternalAttribute` emits for M4A iTunes free-form tags. rsgain's [MP4 writer](https://github.com/complexlogic/rsgain/blob/aae8cc74190de9dafce41576f3e407e62420a51d/src/tag.cpp#L765) writes `----:com.apple.iTunes:replaygain_track_gain/peak`, with configurable key case. The checked writer SHA256 is `f74bb099359cee58e275191ac321b8f05eb7e01455c2448fa9cd5aefc928163a`. This is another source-confirmed format gap, not proof the user's library contains affected M4A files.
