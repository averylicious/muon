## Finding and change

Pinned Media3 sources show URI-only caches in `CacheBitmapLoader`, `MediaSession.Builder.ensureBitmapLoaderIsSizeLimited` and `DefaultMediaNotificationProvider.createNotification`. A title/artist/album change at the same Tauon picture URI can reuse the previous bitmap (or failed future); replacing only Muon's loader would leave the framework caches in place.

Live media items now append a deterministic SHA-256 display-metadata revision as a URI fragment. A replacement title/artist/album gets a different notification cache address; repeated metadata keeps the same address. The fragment contains no raw tags and adds no per-library map. Audio URIs, media IDs, saved handles, artwork byte/dimension limits and request deadlines stay unchanged. Compose canonicalizes only this generated fragment, preserving its existing identity-aware cache and disk filenames.

This revision is a cache hint, not authenticated audio identity. A changed cover with identical title/artist/album and ID is not detected by this policy. Existing queued metadata is not rewritten after a catalog refresh; verification must replace the queue item using the refreshed catalog.

## Additional source finding — embedded separators (2026-10-30)

At combined80348c14, `ArtworkCache.artworkIdentities` joins title/artist/album with NUL separators. Those fields can themselves contain NUL: existing TrackMetadataBudgetTest.nulSafeCodecExpansionCannotBypassTheIncomingRecordBudget and TauonTracklistTest.unicodeEscapesAndFullAlbumMetadataMatchWithoutTagTruncation preserve it. For the same origin/track ID, (title="a\0b", artist="c", album="d") and (title="a", artist="b\0c", album="d") produce the same identity string. The memory key, current-request check, disk key and theme can therefore reuse an old cover despite different admitted display fields. This is an injective-serialization defect, not a SHA-256 collision. It requires this unusual metadata and ID reuse; no actual-library/phone occurrence, changed audio, authentication or saved-ownership impact was demonstrated.

The notification revision uses length-framed fields, and NotificationArtworkRevisionTest.revisionsAreStableDisplayKeysAndNeverChangeTheAudioOrDownloadIdentity already controls this NUL-boundary pair. Compose canonicalizes that generated revision before looking up its older identity, so the notification fix does not clear the in-app issue. A secondary UTF-8 replacement alias remains qualified. Root subsequently checked AOSP17 [JsonReader](https://android.googlesource.com/platform/frameworks/base/+/refs/tags/android-17.0.0_r1/core/java/android/util/JsonReader.java) and [JSONTokener](https://android.googlesource.com/platform/libcore/+/refs/tags/android-17.0.0_r1/json/src/main/java/org/json/JSONTokener.java): each Unicode escape is appended as a single char, without rejecting an unpaired surrogate. Muon's structural preflight/projection/budget adds no such rejection. A clean host-JDK source-run control confirms distinct lone-surrogate strings encode to the same UTF-8 replacement bytes; it did not execute Android's encoder or either platform parser. Disk filenames and notification revisions use UTF-8, so aliasing there is source/host-supported inference, not an Android runtime reproduction; raw-string memory identities remain distinct for this second case.
