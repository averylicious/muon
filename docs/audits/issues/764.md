# #764 — Lyrics ownership when live IDs are reused

Updated2026-10-30. [Owner issue](https://github.com/averylicious/muon/issues/764). Separate post-RC maintenance on `codex/lyrics-owner-oct30`, based main2ec8b69892beda2ef691e0c4b3ac01f1b9e462ef. Frozen .1420/main application/alpha unchanged. No phones.

## Source finding / correction

LyricsScreen keyed its whole state only by mediaId, while the inner fetch effect depends on retry count. If two queued items have the same live ID but different title/artist/album, PlaybackUi updates the header but the existing body/fetch, scroll and collapsed-bar state survive. Root verified the live ID is origin/track number; Add preserves it while adding occurrence/insertion extras. LibraryModel.connect refreshes library state without rewriting the live queue, and MuonApp clears that queue only on explicit Disconnect. The old-queue/new-metadata scenario is source-reachable; it has not been reproduced on a phone.

Extend the outer key with queued title/artist/album plain strings. Identical duplicates retain state; changed artwork, duration or occurrence extras do not reset it. Existing saved-handle early return still performs no Tauon lyric request. No new state framework, queue mutation, network API, tag writing, storage/schema/dependency or signing change.

Labels remain a display revision, not authenticated audio identity. If an old queued item's ID was already rebound on Tauon before Lyrics opened, that server lookup can still return the current ID's words under the old queued labels. This correction does not solve that separate limitation or silently remove stale queue items. It is not a new frozen-RC gate.
