# #690 — Cancel a slow initial library load

Updated 2026-10-24. [Owner issue](https://github.com/averylicious/muon/issues/690). Main base `efea9d5c7f6b73fb0d916577fc18185fdf19b19a`; candidate `codex/connect-load-cancellation-oct24`. Post-RC work, not a frozen .1420 gate. No phones used.

## Finding and implementation

Connect currently disables its address, Connect/server and offline actions while loading. Each finite metadata request has a deadline, but up to 2,048 playlist requests are sequential; those per-call deadlines do not make a whole load short. This is a source-supported missing cancellation control, not a measured device hang or a new infinite-request defect.

During loading, Connect becomes a separate Cancel control at the same location. It revokes the existing `LibraryLoads` token/job, preserving the last published library and address. The current HTTP call uses the existing coroutine cancellation bridge; shared clients/playback are not cancelled. Late results/failures cannot publish through the old owner. Cancellation also marks auto-connect attempted for that screen visit, preventing a discovery result from immediately restarting the load. Background discovery itself remains separate.

The distinct button branch cancels an active pointer gesture when the load completes; releasing an obsolete Cancel must not become a new Connect action. Cancellation does not disconnect or delete a completed library or saved data. Blocking saved-storage reads may still need to unwind before their worker completes; no resources are closed beneath them.
