## Source finding and opposing checks

Official Google Maven Media3 extractor1.11.0 sources SHA256 `76404d34549e50b93f16c94119aace19dee06be9068c45a3d4f8ed5289e4eb3e`:

- `mp4/Mp4Extractor.readAtomHeader` reads the header then allocates a full `ParsableByteArray((int)atomSize)` for its parsed leaf whitelist. It checks minimum header size, requires the ordinary8-byte header for these leaves and size≤Integer.MAX_VALUE, but not the known stream length or parent-container end before allocation. The body is read afterward. Leaves inside `moov` remain attached until that container is processed. This concerns parsed metadata/index leaves, not whole `mdat` media: unparsed boxes are skipped/seeked.
- `mp4/BoxParser.parseStbl` takes a positive Int sample count from `StszSampleSizeBox`/`Stz2SampleSizeBox`. After required chunk/timing headers are read, its normal non-rechunk path allocates offsets/timestamps long arrays and sizes/flags int arrays (about24bytes per declared sample), before iterating sample/chunk data. A fixed-size `stsz` needs no per-sample size payload. High-bit unsigned counts are rejected by `readUnsignedIntToInt`, but large positive counts remain possible. This is conditional on a track and the other required boxes reaching that path, not a claim every tiny malformed file does so.
- `FLAG_OMIT_TRACK_SAMPLE_TABLE` suppresses those normal-path arrays, but Muon uses default flags0. Do not simply enable it: ordinary playback/seek behavior must be preserved. Raw/μ-law/A-law fixed-size audio instead rechunks from chunk declarations; its full allocation path has not been cleared by this assessment.

Main and alpha `ee7ddb7521855a7422036d7cd4f384d11b308caa` both use Media3 1.11.0/default MP4 selection. The leading-ID3 guard and candidate #718's FLAC/Ogg guards do not bound this route. No alpha changes made. A later source check also found fragmented read-time allocation routes below. Nested `ilst`/`udta`/codec configuration and every count source are not cleared by the ordinary MP4 assessment.

## Fragmented-path follow-up

Root source assessment on the same pinned artifact: `FragmentedMp4Extractor.readAtomHeader` also allocates parsed leaves before body bounds; `parseTruns` sums positive declared trun counts and calls `TrackFragment.initTables` before per-sample parsing. That method grows four sample arrays to `(sampleCount *125)/100` (Int arithmetic). A trun can rely on tfhd/trex defaults and carry no per-sample payload. Fragmented initialization still uses the shared BoxParser for ordinary moov metadata. `PsshAtomUtil.parsePsshAtom` version1 sizes a UUID array from keyIdCount before reading those16-byte entries; no executed proof for that path yet. This is not a claim every malformed MP4 reaches every allocation.
