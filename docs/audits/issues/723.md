## Confirmed source boundaries

Official extractor sources SHA256 `76404d34549e50b93f16c94119aace19dee06be9068c45a3d4f8ed5289e4eb3e`:

- `wav/WavHeaderReader.readFormat` reads16 fixed fmt bytes, then allocates the declared extension before peeking its body. The required fixed fields and unsigned sample-rate reads do not cap a positive extension to actual file/metadata bounds. Unknown chunks use physical skip, not whole-payload allocation; whole audio/data length is not this finding.
- `wav/WavExtractor.ImaAdPcmOutputWriter` verifies frames-per-block, then derives input/decoded buffer lengths from target frames (sample rate/10), block size and channel count before sample reading. Field widths and physical fmt backing alone do not impose a practical aggregate writer-buffer budget. Integer intermediate/overflow paths need source review.
- PCM passthrough has no comparable private derived data arrays, but publishes a derived maxInputSize; this needs separate admission/overflow assessment rather than an unqualified whole-decoder claim. RIFF/RF64 headers and supported extensible/IMA formats need positive controls.

Main and the inspected alpha use the same Media3 pin; no alpha changes. Leading ID3, FLAC/Ogg and MP4 guards do not cover WAV-specific fields. Loader catches OOM; amplification is source evidence, not a device outcome.
