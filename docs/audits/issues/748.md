## Finding and correction

TrackList already creates unique keys for repeated IDs, but its click callback discarded the indexed row position. MuonApp supplied only the track ID to prepareLiveQueue, whose documented ID-only behavior selects the first match. Thus tapping the second A in `[A, B, A, C]` starts at the first A instead. This is confirmed source behavior; no device reproduction is claimed.

The row callback now carries its index. Songs/playlist preparation admits that original index and translates it into the full playable queue after filtering unavailable entries. A selected ID must still match the supplied row; missing, unplayable or mismatched selection returns no plan. ID-only callers retain first-match behavior; Play all/Shuffle and Search retain their existing behavior. Search plays the full Songs order, so its filtered-result index is deliberately not used.

Full count/metadata admission precedes player mutation and never returns a prefix. Every playable duplicate stays in the queue with its own occurrence UUID. No new dependency, storage/schema, queue admission limit, shuffle algorithm, package/signing or release behavior.
