## Finding and current correction

QueueScreen starts a suspended showSnackbar caller per removal/refusal; MuonApp does the same for Add/Play next and queue-size refusals. Material serializes these behind a mutex. Dismissing only the displayed notice does not cancel existing native waiters; the refusal path did not even dismiss that one. Bursts retain stale feedback/tickets and can display obsolete notices later. This is separate from the accepted queue identity/order fixes. The same application call pattern is present in inspected alphaEE/frozen6b1; no alpha/library or installed app was changed.

QueueNotices now coalesces only obsolete display-child futures. Superseded callers get Dismissed and reach existing cleanup. A queue display waiting behind an unrelated native caller is cancelled too, so an app-wide shared host does not invalidate the bound. Normal cache/ReplayGain notice producers retain their existing flows.

A public SnackbarData adapter marks an Undo action before calling native performAction. A chosen action is never cancelled by replacement, even if its native continuation has not run. All three Snackbar rendering locations (Scaffold, full-player overlay and QueueScreen) now render through that adapter with the same default Snackbar component; unrelated visual types pass unchanged. Actual queue/admission/Undo work stays outside the display owner. Caller/screen cancellation still removes its own display; immediate dispatch cannot dismiss the new notice. No constructor job, framework-private API, queue order/shuffle/service/storage/dependency/signing/release change. The bound covers obsolete queue display waiting, not every pending controller command, already-acknowledged operation or whole heap.
