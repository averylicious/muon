## Finding / candidate

QueueScreen starts a suspended showSnackbar call for every removal/refusal. Material's native mutex queues these callers. Dismissing the displayed notice does not cancel existing waiters, and the refusal path did not even dismiss that one. Bursts can retain obsolete messages/tickets and display stale feedback later; this is separate from the previously fixed queue identity/order issues.

QueueNotices owns one native display caller and a conflated newest replacement. Superseded pending replies finish Dismissed so each existing removal coroutine reaches its original finally/close. A newest-reference check also handles an old receive already dispatched before a burst. Dismiss before sending to avoid dismissing the new notice under immediate dispatch.

Do not cancel the native display coroutine on replacement: prompt cancellation can erase an Undo action that already won but whose continuation has not run. Complete its original result, then show the newest replacement. Actual acknowledged removal/Undo work remains outside the display owner. Caller cancellation dismisses only its own active display; the screen's existing scope closes worker/mailbox on disposal. No changes to service admission, queue identity/order/shuffle, storage, dependencies, signing or release behavior. This bounds status waiting, not every pending controller command, caller-owned continuation or whole heap.
