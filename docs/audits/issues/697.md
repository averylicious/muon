# #697 — notification artwork work queue

Updated 2026-10-25. [Issue #697](https://github.com/averylicious/muon/issues/697). Inspected main `f0a744273e58645490a1f918a807ad2447d64662`; isolated branch `codex/notification-artwork-queue-oct25`. Post-RC maintenance; no phone use or change to frozen RC .1420.

## Finding and implementation

Pinned Media3 `DataSourceBitmapLoader` submits every URI/embedded decode to its default shared single-thread executor, which has an unbounded waiting queue. `DefaultMediaNotificationProvider` discards obsolete callbacks but does not cancel their work. Muon's current byte/dimension limits bound a single cover, not an accumulation of obsolete requests. Rapid changes behind a slow cover can therefore delay the newest cover and retain queued request state. No device backlog, heap/OOM or relationship to #671 audio buffering has been demonstrated.

The candidate supplies a shared one-worker executor with one waiting slot. New requests replace older pending tasks and cancel their futures; active work retains the physical worker until it actually returns/closes. Cancellation listeners run after publishing the replacement and releasing the submission lock, so a reentrant request cannot orphan a future. A stopped executor returns a failed future. Existing encoded/decode/deadline guards, saved-cover routes and URI-cache behavior remain; no audio/Compose requests or shared network dispatcher are cancelled.

This is a bound on this executor's active/waiting work, not all caller-held futures/bitmaps, metadata/cache wrappers or exact native/ART memory. The current slow request may still run until its existing deadline. Ordinary notification requests normally concern the newest track; older pending covers are deliberately not decoded.
