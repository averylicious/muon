## Settings move-offer count (source candidate, not acceptance)

The Store on SD card switch had read the completed-download index count on main via synchronous `OfflineStore.downloadsOn`, and a failed read became `0`. On this branch the switch saves the preference immediately, as before, then calls the new suspend `OfflineStore.moveOfferCount`. That function:

- **Gate:** takes a process-owned, non-waiting `AtomicBoolean` gate. While the gate is held, any second request, for either shelf, gets `Busy`. It isn't queued.
- **Off-main read:** reads the index count inside `withContext(Dispatchers.IO)` with the original `available()` (storage-barrier) checks and closes the cursor.
- **Results:** after the read it rechecks store/shelf identity, availability and the move exclusion, then returns `Counted(n)`, `Busy` or `Unavailable`. A failed read is `Unavailable`. The synchronous `downloadsOn` now also returns null rather than `0` for a failed read.

**Cancellation:** cancelling the caller cancels only its delivery. `withContext` doesn't return until a blocked read itself returns, so the gate stays held until then.

**UI:** while a count is pending, the switch is disabled and a short "Checking…" line shows; the rest of the screen stays navigable. A result opens the existing confirmation only if all of these still hold:
- the choice and the card shelf are unchanged;
- the store is the same;
- no move has started.

`Busy` and `Unavailable` show a generic one-line message with no raw error. A zero count shows nothing. The count authorizes nothing: `move` keeps all its own checks. StatFs/card-name probes, move/copy algorithms and timing aren't changed or measured here.

**Tests:** `CardAvailabilityRouteTest` wraps the fixture's real `DefaultDownloadIndex`, so the production `moveOfferCount` path runs against a real index whose completed-row read can be held, failed or observed. Three cases:
- **Held read, then cancel:** a read is held on its worker and the caller is cancelled. The caller doesn't finish, card and phone requests are refused without reading, and the cursor closes after release. A later count runs off the calling thread.
- **Failure vs. empty:** a failed read is `Unavailable`, not `0`; a truly empty shelf is `Counted(0)`; an unavailable card isn't read.
- **Shelf replaced mid-read:** this reports `Unavailable`.

No local build was run; CI is the first compile. The Compose delivery, stale checks and messages are covered by source reasoning only. No UI test or device run.
