## Source-confirmed policy gap

Muon gives trusted external controllers transport/read commands and keeps queue/configuration edits with its UI. The own-UID branch also grants Media3's in-process notification controller full default commands and custom queue Undo authority. Pinned Media3 publishes that grant into its legacy/platform session. With notification connected, `MediaSessionImpl.onConnectOnHandler` supplies that platform result for System UI, and `resolveControllerInfoForCallback` aliases those requests to the notification controller. Direct callback fixtures alone miss this path.

Google Maven `media3-session:1.11.0` sources SHA256 `9fa36c24ead02c89325d5b89d5322f2781b1b50511d1b432b4b033ab3c38e715`; inspected `MediaSessionImpl` connection/update/resolve methods, legacy platform result and browser connection, plus the supported `MediaSession.isMediaNotificationController` classifier and public connection-hint key. The deprecated default onConnect delegates into onConnectAsync; no separate legacy-callback bypass was found. The classifier is used only to **narrow** an already-own-UID grant, not as proof of identity.

This is overbroad authority relative to Muon's policy, not a confirmed package-name-impersonation exploit or privacy incident. The playback service is non-exported. Android token access, package visibility, calling-UID propagation and actual System UI/Bluetooth behavior remain untested here; do not revive the earlier withdrawn spoofing claim.
