## User evidence and required behavior

User screenshots show Delete confirmation followed by Muon's own `SavedRemoval.NotOwned` toast: “Muon can't tell that copy's bytes belong to it alone, so it was kept.” This is Muon's ownership decision, not an Android permission dialog. One message currently represents several checks, so it does not identify the exact failing condition or prove shared bytes. User requires explicit Delete to work normally; Unverified against Tauon is not a deletion prohibition. Concrete unavailable storage/I/O or a proven unsafe path may fail with an actionable explanation. Do not merely hide Delete or erase another copy.

The user later clarified the sequence: old files survived a POCO factory reset **on the SD card**, the refusal happened afterward, and Muon data was subsequently cleared out of frustration. The original failing private state is no longer available. The surviving-card/rebuilt-index scenario is a hypothesis for controlled testing, not a confirmed cause. Muon source does not read SSAID/ANDROID_ID in this ownership path; Media3's on-disk cache UID is a separate identifier.
