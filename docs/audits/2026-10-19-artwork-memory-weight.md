# Bound artwork memory keys as well as bitmap bytes (#253)

Inspected cumulative #63386a835b9296961f4c95adbdb73328fe14bacd747/main a2db02b8ba0b4959f28aecf5fa89196cf92622bc. Artwork.kt used a12MiB LruCache charged only by Bitmap.byteCount. A1×1 image costs only a few pixel bytes, allowing a large number of URL/identity keys across refresh generations without reaching that bitmap-byte cap. The selected .1296 real-artwork test used larger artwork, so it does not settle this tiny-image/cardinality case. No phone OOM or malicious library was demonstrated.

Keep the existing LruCache/load/publication protocol, but weight the larger of byteCount/allocationByteCount plus UTF-16 URL/identity payload and128bytes per-entry allowance, with a minimum32KiB per entry. Production12MiB then retains at most384 keys; metadata above that floor contributes to eviction too. This is logical weighted cache accounting, not exact ART/native retained bytes or a whole-process cap. A single over-budget value is charged at budget+1, enough for non-retention without overflowing the cache's Int accumulation (factory budgets cannot exceed12MiB). Existing key identity/size/origin, late-publication rejection, two-load concurrency, artwork decode limits and disk/saved-cover stores are unchanged. Eviction does not recycle a bitmap a visible/crossfading component may still hold.

Two actual Android LruCache/Bitmap regressions (Robolectric API34):1,200 tiny shared-image keys across three library generations retain only the newest384 and leave the visible shared bitmap usable after eviction/clear; long URL/Unicode identity payload exceeds the floor and evicts sooner, oversized metadata is not retained and subsequent normal admission still works. Reuse one bitmap in the tiny case to emphasize metadata/cardinality rather than create an uncontrolled image-memory fixture. Existing identity/theme/size/disk/concurrency cases remain. CI is first Android compile/tests; no local build.

Tradeoff: tiny images may refetch sooner than the old pixel-only budget allowed; large usual thumbnail retention changes only by the added metadata charge. No exact runtime memory/speed gain claimed. Actual final-head APK verification and optional tiny-image device characterization remain separate from user visual/hardware/spoken acceptance. Previously installed .1309 does not contain this change. No saved audio/cover/native migration/removal change, no dependency/schema/settings/network/release/production activation.
