# Card download-index identity characterization — 2026-10-01

Inspected main: `b14bc8f0635f5fc754caeade13d535bcceb3f2c9`. Continues the existing #179 volume-identity concern; no new app behavior, volume identifier, migration or storage fix. GPT-6 / Codex desktop (Sol), effort not reported; author investigation/implementation, no independent review.

OfflineStore creates each card cache in that card's directory but always supplies DefaultDownloadIndex(database, "card") backed by the phone database. Shelf.completed trusts that download record; downloadedOn, downloadedSongs and routeOfflineRequest inherit it without establishing that the attached card has the bytes. A newly attached different card can therefore inherit completed records belonging to the previous card. The separate cache content UID does not namespace the download index. Existing no-live-reattachment and DownloadService helper ownership limits remain separate; this fixture does not imply a current live card swap implementation.

CardIndexCharacterizationTest uses actual pinned Media3 caches/DownloadManager/DefaultDownloadIndex with native SQLite, different disposable directories, exact tiny bytes and the real Muon completion/listing/routing functions. Reflection only attaches/restores a disposable Store; it does not change those decisions. Three cases cover same mounted-card reopening, different empty card with the shared index, and a distinct-index control. CI is the first actual compile/execution; final results belong on the PR.

The shared-index case expects the currently unsafe outcome: the empty card is reported complete, listed with the previous card's offline metadata and selected by the offline route despite missing bytes. No service, upstream network read, phone mount event, wrong audible song or user-data loss is reproduced. Mounted orderly release isolates this identity problem from #192's separately characterized absent-cache index-loss sequence. The control is not a proposed production namespace or migration; cache/download identity must be designed around actual volume availability and preservation of existing indexes.

#179 remains open and unfixed. Next production design needs persistent per-volume download/index ownership, safe absent-card handling, old shared-index migration without deleting bytes, same/different-card rules and service-helper coordination. Actual mount/hot-swap and active operations need separately authorized device QA with disposable copied data. No phone QA is needed for this test-only PR; its passing unsafe-outcome assertions are not fix verification.
